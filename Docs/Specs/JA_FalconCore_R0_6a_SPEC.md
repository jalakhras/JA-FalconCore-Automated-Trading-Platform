## 0. لماذا R0.6a — ونطاقها بدقّة

`CFalconReportWriter` أكبر كلاس في المشروع (6,292 سطرًا = 36%). R0.6 كلّها
أكبر مرحلة في إعادة الهيكلة، لذلك قُسّمت:
- **R0.6a (هذه):** تفكيك بنيوي. ننقل ReportWriter إلى `Reporting/`،
  مقسّمًا إلى ملفات `.mqh`. **كل التقارير ما زالت تعمل تمامًا كما الآن.**
  صفر تغيير سلوك.
- **R0.6b (لاحقًا):** إضافة مفاتيح `input` للتقارير التشخيصية وإطفاؤها
  افتراضيًّا. (تغيير سلوك مقصود ومنفصل.)

**ما لا يحدث في R0.6a:**
- لا إطفاء لأي تقرير — كلّها تعمل.
- **لا لمس سلسلة الـ 12 `Apply*`** — تبقى حيث هي (تُفصَل في R0.7).
- لا لمس منطق Lock Parity Decomposer.
- لا تعديل دوال الـ telemetry للبروكر.

## 1. القيود الصارمة

- **صفر تغيير سلوك.** كل تقرير يُنتَج كما الآن، بنفس المحتوى بايت-ببايت.
- لا تعديل منطق، لا تعديل input، لا حذف وظيفة، لا إطفاء تقرير.
- **لا لمس الـ 12 `Apply*`.** إن كانت داخل ReportWriter، تبقى داخل الملف
  الذي ينتقل إليه جسم الكلاس — تُفصَل في R0.7، لا الآن.
- النقل = قصّ + لصق + `#include`. لا إعادة كتابة منطق.
- لا نقل globals.

## 2. تحدّي R0.6a — كلاس واحد، عدّة ملفات

`CFalconReportWriter` كلاس **واحد** ضخم. تقسيم كلاس MQL5 واحد على عدّة
ملفات `.mqh` ممكن بإحدى طريقتين — اختر الأنسب بعد فحص الكود:

**الطريقة أ — تقسيم تعريف الكلاس عبر `#include` داخلي:**
ملف رئيسي للكلاس `Reporting/FalconReportWriter.mqh` يحوي `class
CFalconReportWriter { ... };`، وداخل جسم الكلاس تُضمَّن أجزin المنهجيات
عبر `#include`. (MQL5 يدعم `#include` داخل جسم الكلاس.)

**الطريقة ب — إبقاء الكلاس ملفًّا واحدًا كبيرًا الآن:**
إن كان تقسيم الكلاس الواحد محفوفًا بالمخاطر، انقل `CFalconReportWriter`
كاملًا إلى ملف واحد `Reporting/FalconReportWriter.mqh`، وأجّل تقسيمه
الداخلي إلى R0.6b أو R0.9. الأولوية: نقله خارج الملف الرئيسي بأمان.

> **القرار:** ابدأ بالطريقة ب (نقل آمن لملف واحد) إن كان تقسيم الكلاس
> يتطلّب إعادة ترتيب منطق. الطريقة أ فقط إن أمكن تقسيم نظيف بلا مخاطر.
> سلامة "صفر تغيير سلوك" أهمّ من جمال التقسيم في R0.6a.

## 3. ما يُنقَل في R0.6a

| الملف الهدف | المحتوى |
|---|---|
| `Reporting/FalconReportWriter.mqh` | `CFalconReportWriter` كاملًا (6,292 سطرًا) — أو مقسّمًا إن أمكن بأمان |
| `Reporting/FalconReportingInputs.mqh` | inputs/macros التقارير التي يحتاجها الكلاس قبل نقطة تعريفها (إن لزم) |

إن قُسّم الكلاس (الطريقة أ)، الملفات المقترحة تحت `Reporting/`:
- `core/SummaryWriter` + `core/TradeLifecycleWriter` — منطق التقريرين
  الدائمين.
- `diagnostic/` — بقية كتاب التقارير.
لكن **هذا اختياري في R0.6a** — الأولوية النقل الآمن.

> ملفات placeholder في `Reporting/` و`Reporting/core/` و
> `Reporting/diagnostic/` تُحذف بعد إنشاء الملفات الحقيقية.

## 4. ترتيب الـ `#include` — حسّاس

`CFalconReportWriter` له علاقات تبعية مهمّة:
- الكلاسات الأخرى (وخاصّةً `CFalconBrokerEntryBridge`) **تستدعي**
  ReportWriter — 6 دوال telemetry (من مراجعة R0.4 §3.6).
- لذلك ReportWriter يجب أن يُضمَّن **قبل** `Execution/FalconBrokerEntryBridge.mqh`.

الترتيب:
```cpp
// ... Core / Evidence / Risk / Execution العليا / Router ...
#include "Reporting/FalconReportingInputs.mqh"   // إن لزم
#include "Reporting/FalconReportWriter.mqh"      // ← قبل جسر البروكر
// ... بقية الملف الرئيسي ...
#include "Execution/FalconBrokerEntryBridge.mqh" // يبقى بعد ReportWriter
```
كل ملف بحارس تضمين.

## 5. بروتوكول "راجع وأصلح أثناء النقل" — إلزامي

عند النقل، افحص:
1. **lookahead:** هل أي كود تقرير يقرأ شمعة غير مغلقة؟
2. **globals:** أي `g_` يستخدمه ReportWriter — سجّله (لا تنقله).
3. **منطق ميت:** تقارير/فروع لا تُستدعى أبدًا.
4. **أخطاء صامتة:** فشل كتابة ملف لا يُبلَّغ عنه.
5. **حدود الـ `Apply*`:** سجّل بدقّة أين تبدأ وتنتهي كل دالة من الـ 12
   `Apply*` داخل ReportWriter — خريطة دقيقة لـ R0.7.
6. **دوال telemetry البروكر الستّ:** سجّل أسماءها ومواضعها.

كل ما يُكتشَف → `Docs/ReviewNotes/R0_6a_Review_Notes.md`.
